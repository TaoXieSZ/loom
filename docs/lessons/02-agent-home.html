第二课：agent home —— 状态到底该住在哪里

loom 教学系列。读完这课，你能说清为什么 agent 的状态要聚合成一个目录、 为什么索引只是"派生物"，以及两级记忆和蒸馏是怎么配合的。写 M2 代码之前先过这一课。

1. 问题：状态三家分管是 v1 的病灶

v1 里一个 agent 的状态散在三处：配置在 dispatch 的数据库里，记忆在一个独立服务里， 会话历史又贴在 loop 的运行时里。后果我们都尝过——改一处要对三处账，重启丢一半， "这个 agent 到底是谁"没有单一答案。

v2 的答案（蓝图 D3）朴素到近乎无趣：一个 agent = 一个目录。

agents/<id>/
├ agent.json      身份+配置+grants（能力边界也住这里）
├ memory/
│  ├ core.md      常驻记忆（每次请求都进 system prompt）
│  ├ facts/       一事一文件的长期事实（靠检索取回）
│  ├ episodes/    按天的经历摘要（蒸馏产物）
│  └ index.sqlite † 检索索引——† = 派生物，删了能重建
├ sessions/*.jsonl  会话历史（一行一条消息）
└ audit.log         审批/工具执行的流水账

这个目录就是聚合根：要备份一个 agent，tar 这个目录；要删掉一个 agent， rm -rf 这个目录；要迁移到另一台机器，整个目录搬过去就完事。 没有第二个需要同步的地方。

2. 文件优先，索引皆派生物

为什么用普通文件（md、jsonl）而不是数据库当真相？三个理由：

  • 人可读可改。core.md 你想改就用编辑器改，不用写 SQL、不用等管理界面。 教学项目尤其如此——状态必须能 cat 出来看。
  • 工具链免费。git 可以版本化它，grep 可以搜它，rsync 可以搬它。
  • 崩溃半写损失小。jsonl 是 append-only：断电最多坏最后一行， 加载时跳过坏行就是（我们的 loadSession 正是这么做的）。

但文件有个短板：检索慢。所以才有了 index.sqlite——它是 FTS5 全文索引， 专门服务 memory_search。关键的心智模型是：

索引是派生物，不是真相。 真相在 md 文件里；sqlite 删了， 扫描一遍 facts/ + episodes/ 就能原样重建。所以过期检测可以很粗暴： 任一源文件的 mtime 比索引新 → 整个重建。几秒的事，不值得做增量同步 那套一致性机制。

这个"真相唯一、索引可再生"的分工，让 M2 完全不用处理双写一致性问题—— 写路径只碰文件，索引永远跟在后面追。

3. 两级记忆：常驻 vs 检回

人记东西也分两档：张口就来的，和"我记得我记过、得翻翻"的。agent 一样：

  • core.md —— 常驻。每次请求都拼进 system prompt。它是 agent 的"自我"： 我是谁、主人是谁、雷区是什么。因为它进每一次请求，必须严格小 （我们硬截断到 2000 字）——core.md 每胖一个字，每一次调用的成本都跟着涨。
  • facts/ + episodes/ —— 检回。量大，不可能全塞进上下文；平时躺在磁盘上， 模型觉得需要时调 memory_search 工具查回来。

注意 core.md 不进索引：它已经常驻了，再索引它只会污染搜索结果 （每次搜索都命中常驻内容，等于没搜）。索引只覆盖"不在上下文里的那部分"。

memory_search 是个只读工具，风险天然低，所以它声明 defaultMode: "always"—— 不打扰人。这呼应 types.ts 里的设计：风险知识属于工具，策略属于 agent 配置。

4. FTS5 trigram 与 CJK 的 ≥3 字符坑

SQLite 的 FTS5 自带 trigram 分词器：把文本切成连续 3 字符的滑窗 （"我喜欢深烘" → 我喜欢 / 喜欢深 / 欢深烘）。这对中文是救星—— FTS5 默认分词器按空格切，整段中文是一个"词"，根本没法检索； trigram 不看空格，中日韩文本天然可搜。

但有个实测踩出来的坑（真机来信级别，写进代码注释了）：

trigram 要求查询词 ≥ 3 个字符。"深烘咖啡"能 MATCH 到，"深烘"不能—— 两个字符连一个完整 trigram 都构不成，MATCH 静默返回空。

所以 memory-index 的查询策略是双通道 + 逐词独立：

查询按空白切词，逐词独立查
  ├ 词 ≥3 字符 → FTS5 MATCH（限定 title/body 两列）
  └ 词 <3 字符 → 回退 LIKE %词%（慢，但正确性优先）
结果按"命中了几个词"降序 —— OR 语义，不是 AND

两个坑都是真机教出来的：

  • **AND 太脆。**第一版是多词 AND：模型的查询是自然语言"咖啡 偏好 喜欢"， 只要"喜欢"不在正文就整体 miss——真机 smoke 里模型明明调了 memory_search， 却回答"没有相关记忆"。搜索引擎的常识是 OR + 按命中词数排序，不是 AND。
  • **FTS 默认索引所有列。**kind/path 也在表里，不框 {title body} : 的话， 查 "fact" 会命中每一条 fact。

短词查询失去了索引加速（全表扫），但对记忆库这种 KB~MB 级的数据量， LIKE 的代价可以忽略。正确性优先，性能够用就行。

5. 蒸馏：压缩内化，不是归档

sessions/.jsonl 会无限长大，但它*不进上下文——历史只按 session 加载， 跨 session 的"我从经历里学到什么"靠蒸馏（蓝图 D4）：

cron 定时跑 scripts/distill.mjs
  ├ 读每个 session 的增量行（watermark 记在 memory/distill-state.json）
  ├ 把增量交给模型："压缩成一段当日 episode + 若干条原子事实"
  ├ 模型吐 JSON → 写 episodes/YYYY-MM-DD.md + facts/<slug>.md
  ├ 重建索引（新记忆立刻可搜）
  └ 推进 watermark（下次只处理新增量）

为什么叫"内化"而不叫"归档"：归档是把原文挪个地方，检索时还得读原文； 蒸馏是让模型把经历改写成人格知识——"7 月 26 日主人让我查深烘咖啡的牌子" 变成 fact："主人喜欢深烘咖啡"。下次对话检索回来的是结论，不是流水账。 v1 的 rotation/memory_key 补丁想解决的正是这个问题，但它在别人的 loop 里 无从下手；自有 loop 里，它就是几十行代码加一个 cron。

watermark 的设计同样体现"派生物"哲学：distill-state.json 丢了， 大不了把全部历史重新蒸馏一遍——结果等价，只是多花时间。没有任何状态是 丢了就出事的。

6. 会话落盘：system 不落，断点如实

sessions/<sid>.jsonl 每行一条消息：{"ts":..., ...Message}。两条纪律：

  1. system 消息不落盘。system prompt = agent.json 的 systemPrompt + core.md 现拼——它本质上是"配置的投影"，落盘会产生第二份真相（改了 core.md， 旧 session 里的 system 还是老的，对账地狱）。加载时现拼，永远新鲜。
  2. 中断/异常也如实落已有部分。turn 跑到一半用户断开， 已经产生的 assistant/tool 消息照落。jsonl append-only 让"落一半" 是正常状态而不是损坏——下次加载从断点继续就是。

实现上有个顺水推舟的点：runTurn 本来就就地追加 messages 数组 （② 层注释里写明这是为了调用方可以直接存盘）。host 只要在 turn 前记下 数组长度，turn 后把新增段切片 append 进 jsonl，一行多余的状态都不用管。
